# Running on the GN100 — day-of runbook

Target: Acer Veriton GN100, GB10 Grace Blackwell. Grace is **aarch64**, so
wheels must match that, not x86.

---

## On the GN100, once

```bash
sudo apt update
sudo apt install -y openssh-server        # note: "install", not "intall"
sudo systemctl enable ssh --now
systemctl status ssh --no-pager
ip -4 addr | grep inet                    # note the address you will SSH to
```

## From your laptop

```bash
# 1. clone, install the right CuPy wheel, cache the catalogue, preflight
./scripts/remote.sh setup user@GN100_ADDRESS

# 2. the numbers for the pitch — CPU vs GPU, measured
./scripts/remote.sh bench user@GN100_ADDRESS

# 3. run it, tunnelled to your laptop browser
./scripts/remote.sh run   user@GN100_ADDRESS
#    then open http://localhost:8760
```

`run` opens an SSH tunnel. **You browse on your laptop; every calculation happens
on the GB10.** Nothing is exposed to the venue network, which also means you do
not care whether Tailscale is behaving.

## If SSH is not available

The server binds `0.0.0.0`, so from the same LAN you can point a browser at
`http://GN100_ADDRESS:8760` directly. Or work on the box itself:

```bash
git clone https://github.com/qimmune/project-kessler.git
cd project-kessler && ./scripts/bootstrap.sh && ./scripts/run.sh
```

## First thing to check

```bash
./scripts/remote.sh setup user@GN100_ADDRESS
```

ends in preflight. The line that matters:

```
✓ accelerator: cupy on NVIDIA GB10
✓ unified memory confirmed — 128 GB shared, host↔device copies are pointer handoffs
```

If instead you see `no CuPy/CUDA`, the wheel did not match the driver:

```bash
ssh user@GN100_ADDRESS 'nvidia-smi | head -3'          # what CUDA major version?
ssh user@GN100_ADDRESS 'cd ~/project-kessler && \
  .venv/bin/pip install cupy-cuda13x'                  # or 12x, to match
```

If no wheel exists for that combination, the demo still runs on NumPy — slower,
and the transfer counter reads zero for a different reason. Say so if asked
rather than implying the GPU is doing work it is not.

## Expected shape of the result

Measured on an M-series laptop, CPU only, for comparison:

| Workload | Time | States | Rate |
|---|---|---|---|
| Fleet sweep (60 assets) | 6.43 s | 405,605,160 | 63 M/s |
| Maneuver trade space | 12.75 s | 148,696,790 | 12 M/s |

`scripts/benchmark.py` runs the same two workloads on the GB10, then re-runs
them pinned to CPU in a clean interpreter so the comparison is like-for-like.
**Screenshot that output** — it is the most defensible slide-free artifact you
have, because every number in it was timed rather than projected.

## Turning the demo up

The knob to move on stage is **Assets protected**. Measured on CPU:

| Assets | Time | States |
|---|---|---|
| 12 | 3.0 s | 81 M |
| 120 | 10.7 s | 811 M |
| 300 | 26.0 s | **2.03 B** |
| 500 | 51.3 s | 3.38 B |

It scales sub-linearly because the catalogue is propagated once and reused for
every asset. If the GPU brings 300 assets down to a couple of seconds, run the
recording at 300 and say the number.

`KESSLER_SCREEN_CHUNK` (default 1500) trades memory for fewer, larger kernels.
On 128 GB there is room to raise it substantially; measure rather than assume.

## Known-unknowns going in

- **The CUDA path has never executed on real hardware.** It has been driven
  through a strict CuPy stand-in (`tests/test_gpu_path.py`) that rejects
  host/device mixing the way CuPy does, and it passes clean with no device
  arrays leaking into results — but a shim is not a GPU.
- **No Nemotron endpoint has been called.** The adapter is tested against a stub.
  Bring up the NIM, then `./scripts/remote.sh bench` and the preflight line will
  tell you whether it answers.
- If either turns out broken, the demo degrades rather than dies: NumPy instead
  of CuPy, deterministic solver instead of Nemotron. Both are honest to say out
  loud.
